# REDLINES.md — AgentBoard compliance sweep

Every safety red line from the Agent ID Hackathon announcement
(https://www.binance.com/en/support/announcement/detail/95f5dbe0ea674a48a739b59e046648bf),
checked line by line against this entry. Verified 2026-11-18 against the
shipped contract source and frontend in this repository.

| # | Red line (announcement) | How AgentBoard complies | Verify |
|---|---|---|---|
| 1 | **No web-based QR-code login for Agentic Wallet.** No scanning QR codes or entering pairing codes on third-party websites to sign in; no storing users' login sessions on servers to place orders on their behalf. | The frontend has no login system at all. It uses the standard injected-wallet flow (`window.ethereum` + `eth_requestAccounts`) — the same connection model as any regular dApp. No QR codes, no pairing codes, no backend server, no sessions: the page is one static HTML file and holds nothing between visits. It never places orders — there is nothing to order; the only transactions are the user's own directory writes. | Read `frontend/index.html`: search for `qr`, `pairing`, `localStorage`, `sessionStorage` — no matches. The only wallet call is `eth_requestAccounts` and contract method sends the user confirms. |
| 2 | **No bypassing user transaction confirmation.** For any operation involving user assets, users must be able to see and confirm the action themselves. | AgentBoard involves **no user assets at all** (see #3). On top of that, every state-changing action (register, update, remove, check in) is a plain contract call sent through the user's own wallet, which displays and confirms it. No meta-transactions, no relayers, no pre-signed payloads, no "sign once, act later" patterns anywhere in the code or copy. | `frontend/index.html` `doTx()` — the single write path — calls the contract via the user's signer and waits for their wallet's confirmation. Contract source has no signature-verification or delegate-execution functions. |
| 3 | **No unauthorized asset transfers.** No scheduled collection, no automatic transfers to fixed addresses, no bundled extra transfers, no soliciting unlimited approvals without the user's knowledge. | The contract has **zero payable functions**, no `transfer`/`transferFrom`/`approve` calls, no token interfaces, and no way to receive or move funds. The frontend never requests a token approval of any amount. Interactions cost only the network gas of the user's own transaction. | `grep -n "payable\|transfer\|approve\|call{" contract/src/AgentBoard.sol` — the only hits are in comments stating their absence. The ABI (`contract/abi.json`) contains no asset-moving function. |
| 4 | **Contracts must be open-source with disclosed owner permissions.** Minting, tax changes, pausing, freezing, withdrawing user funds — any such permission must be clearly documented. | Fully open-source (MIT) and verified on BscScan from this exact source. **Owner permissions: none exist.** The contract has no owner, no admin role, no mint (it issues nothing), no pause, no freeze, no withdrawal function, no upgrade path, and no setter of any kind. Its only configuration is the `agentIdRegistry` address, an `immutable` set once in the constructor. The deployer (the project's Agentic Wallet) retains zero power after deployment — there is no function it can call that any other address cannot. | Read `contract/src/AgentBoard.sol` end to end (one file, ~250 lines): the complete function list is `register`, `updateProfile`, `removeProfile`, `checkIn`, and view functions. Constructor takes only the registry address. |
| 5 | **No impersonation of the Binance brand.** Project names, token names, and domain names must not use "Binance" / "BNB" to impersonate the official brand. | The project is named **AgentBoard**. There is no token. The site is served from the author's own GitHub Pages domain (`bondan0.github.io/agentboard/`). The words "Binance" and "BNB Chain" appear only in factual references (the chain the contract lives on; the app where Agent IDs are claimed; the hackathon's name in the README's context section), never as branding, logos, or implied affiliation. The footer states plainly: *"AgentBoard is an independent community project … not affiliated with, endorsed by, or operated by any exchange or platform."* The visual theme (indigo/slate) deliberately does not mimic any exchange's brand identity. | `frontend/index.html` header + footer; README "Hackathon context" section. |
| 6 | **No collection of sensitive credentials.** No seed phrases, private keys, API secrets, or pairing codes. | The frontend collects nothing: no accounts, no forms other than the listing fields (category, endpoint, description) that the user intentionally publishes on-chain, no analytics, no backend to send data to. It never asks for a signature other than the wallet's own transaction confirmation for the user's own action. | `frontend/index.html` — the only inputs are the three listing fields and the search box; there is no `fetch`/`XMLHttpRequest` to any endpoint except the public chain RPC used through ethers.js. |
| 7 | **No promising returns.** Terms such as "passive income" or "automatic money-making" are prohibited in external communications. | A copy sweep of every shipped file (contract comments, frontend, README) found **no** occurrence of: "passive income", "automatic money-making", "earn", "profit", "guaranteed", "returns", "yield", "investment". The product is a directory; it has no token, no staking, no fees, and nothing that could pay anyone anything. Hackathon prize information appears only in this compliance file and the README's factual context section, describing the event — not as a promise to users. | `grep -niE "passive income|money-making|earn|profit|guarantee|yield|invest" frontend/index.html README.md contract/src/*.sol` — no matches in user-facing copy. |
| 8 | **Products involving trading must display risk warnings.** | Not applicable — AgentBoard has no trading functionality, no prices, no orders, no markets. ("Trading" exists only as one of the category labels a listed service may choose for itself.) The footer nonetheless carries a plain-language disclaimer of non-affiliation and of the contract's no-funds design. | `frontend/index.html` footer. |
| 9 | **Agent ID must not be packaged as a tool for "looking up other people's wallets by name."** | AgentBoard is a **service directory, not a people directory**. It contains only services whose owners deliberately registered them, and the only names displayed are those owners' own identities on their own listings. There is no search-by-name over Agent ID holders, no enumeration of holders, and no feature that resolves an arbitrary person's wallet from their name for the visitor's use. `handleOf` is used for exactly two things: (a) the contract binding a listing to its *creator's own* identity at registration time, and (b) showing a connected user *their own* name. The public read surface is the opt-in listing set (`getProfiles`), nothing else. | README "Why Agent ID is the core" and "Safety & permissions"; frontend renders only registered listings. |
| 10 | **No abnormal behavior**: no malicious volume manipulation, no illegitimate mass account registration for interactions, no market manipulation. | Interactions are organic by design: each Agent ID is one-per-person and non-transferable, so one real holder = at most one profile and one daily check-in — the contract's own rules make mass fake interaction structurally pointless (a second check-in the same day reverts; a second profile reverts). The project runs no incentive, reward, or airdrop promise that would motivate farming, and the team interacts only with its own single Agent ID (bool01.ai) for the project's own listing and testing. | Contract rules: `AlreadyRegistered`, `AlreadyCheckedInToday` errors; one-Agent-ID-per-address property of the registry itself. |

## Standing posture (from the project's own safety rails)

- User funds only; nothing in this project touches funds at all.
- Deployment and every later contract call go through preview → explicit
  confirmation → execute; nothing is broadcast on a user's behalf silently.
- If any future feature would move an asset, request an approval, or add a
  privileged function, this file must be re-swept before it ships.
